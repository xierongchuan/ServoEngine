# Очистка проекта и запуск с чистыми данными

Рабочие `data/`, `charts/`, Python/test/build-кэш, `node_modules` и временные lock-файлы конфигурации не входят в Git. `requirements.lock` и `package-lock.json` — файлы зависимостей, они остаются в репозитории. `.dockerignore` также исключает данные, архивы и runtime lock/tmp из образов.

**Данные для восстановления торговли — не временные файлы.** Очистка не должна превращать UNKNOWN-ордер, открытую позицию или durable-паузу в «чистый» счёт.

## Команды

Из корня проекта, с установленным Podman и собранным bot image:

```bash
# Только показать план. Можно выполнять при работающем стеке.
./scripts/clean_project.sh
./scripts/clean_project.sh --mode reset

# Применять только после остановки всех писателей — см. порядок ниже.
./scripts/clean_project.sh --mode cache --apply
./scripts/clean_project.sh --mode reset --apply
```

`--dry-run` явно включает предварительный просмотр; это поведение по умолчанию. Без `--apply` файлы не изменяются. Скрипт не задаёт вопросов в терминале и не запускает сервисы автоматически.

Python выполняется **только внутри Podman**, без сети, передачи `.env` в окружение и биржевых запросов. Запускается отдельный контейнер, не `compose run`. Скрипт читает только необходимые State/Mounts из `podman inspect`, без `Config.Env` других сервисов. Для нестандартного имени уже собранного образа можно задать `SERVO_CLEANUP_IMAGE`. Исходник очистки берётся из текущего checkout, а не из старого образа.

## Что очищается

| Объект | `cache` | `reset` |
|---|---|---|
| Свечи `data/prices/`, `data/market_data/`, `data/instances/*/prices/` | Удаляются восстановимые файлы | Переносятся в архив |
| Новости, PNG-графики в `charts/` и `data/charts/` | Удаляются | Переносятся в архив |
| `__pycache__` в src/tests/scripts, `.pytest_cache`, frontend `dist/` | Удаляются | Переносятся в архив |
| История сделок, журнал решений, backtest result | Сохраняются | Переносятся в архив, включая instance decision journals |
| Structured/text-логи и известная `data/logs/events.sqlite3` | Сохраняются | Переносятся в архив вместе с SQLite sidecars |
| Runtime/worker command/status, веб-токены панели | Сохраняются | Переносятся в архив; ссылки входа потребуется получить заново |
| `.env`, весь `config/`, исходники, dependency lock-файлы | Сохраняются | Сохраняются |
| Active trades, position owners, GRID/Spot/execution journals, защитные lock/guard | Сохраняются | Сохраняются |
| `exchange_rate_limits.sqlite3` и её WAL/SHM/guard | Сохраняются | Весь комплект переносится в архив; при следующем запуске создаётся заново |
| Неизвестные файлы вне разрешённых областей, `node_modules`, `.cache/` с wheels/private probes | Сохраняются | Сохраняются |

Символические ссылки в очищаемых областях вызывают отказ; внешние каталоги не обходятся. SQLite с произвольным именем и её sidecars не считаются обычным кэшем. Под именем `events.sqlite3` принимается только точная известная логовая схема, не торговый журнал. Пустые каталоги могут оставаться — это нормально.

`reset` даёт свежие свечи, графики, историю, логи, control channel и rate limiter, **но не стирает торговую память безопасности**. Пустые файлы не заменяются на `{}`: приложения штатно создадут отсутствующие файлы с правильной структурой при следующем запуске.

### Полный сброс rate limiter

При явном `--mode reset --apply` после остановки всех писателей убирается весь комплект: основная SQLite, `-wal`, `-shm`, `-journal` (если есть) и `.guard`. На следующем запуске `ExchangeRateLimiter` автоматически создаёт новую базу и guard — вручную готовить файлы не нужно. Остаточный guard при отсутствующей основной БД тоже архивируется явным reset.

Сохранённый cooldown при этом сбрасывается сознательно. Первый успешный запрос **не гарантирует**, что биржа сообщит оставшийся бюджет или время до снятия ограничения. Если биржа вернёт 429/Retry-After, существующая обработка сохранит новое ожидание. Поэтому обычный `cache` лимитер не трогает, а `reset` явно предупреждает о сбросе.

Потеря только основной БД при оставшемся guard во время обычного запуска по-прежнему считается ошибкой: это защита от случайной потери состояния работающего процесса, а не запрет намеренной полной очистки. Не удаляйте SQLite sidecars вручную при работающем стеке. Схема основной БД проверяется перед reset: торговый журнал под именем rate limiter не будет стёрт.

## Порядок безопасного сброса

1. Проверьте реальные позиции и ордера на бирже. Команда очистки **не закрывает позиции, не отменяет ордера и не проверяет счёт через API**. UNKNOWN/pending сначала разрешаются штатной сверкой, не удалением файлов.
2. Остановите runtime штатно и дождитесь завершения. Затем остановите **оба** контейнера, включая панель — она тоже пишет логи и токены:
   ```bash
   podman compose --profile panel stop bot panel
   ```
   Остановки только торговли кнопкой в панели недостаточно: supervisor остаётся писателем. Остановите также foreground-боты, тесты и любые другие процессы с этими данными.
3. Выполните `./scripts/clean_project.sh --mode reset`, изучите план.
4. Выполните `./scripts/clean_project.sh --mode reset --apply`. Не запускайте другие процессы/контейнеры с проектом параллельно проверке и очистке.
5. Проверьте сообщение об успехе и архив с `complete: true`. При отказе или частичном сбое **не запускайте** рабочий стек до проверки архива и оставшихся файлов.
6. Перед новым запуском проверьте `config/trading.json`. Очистка **не меняет execution**: если раньше был `live`, он останется `live`. Для безопасного первого запуска выберите `read_only` штатным способом. Используйте обычный согласованный порядок запуска из [CONTAINERS.md](CONTAINERS.md); `SERVO_RUNTIME_START_ON_BOOT` может автоматически запустить runtime.

Перед применением проверяются все контейнеры текущего Podman, а не только имена `servoengine_*`: running/paused/restarting контейнер с mount проекта, его подкаталога или родителя запрещает операцию. Дополнительно проверяются свежие runtime/worker statuses. Ошибка проверки — отказ, а не разрешение очистки. Скрипт не останавливает контейнеры сам.

Для `reset` вызывается тот же fail-closed guard, что защищает смену execution: открытое владение, незавершённые заявки, паузы и неизвестное/повреждённое состояние запрещают сброс. Committed WAL читается без `immutable`. Локальная проверка не заменяет сверку счёта. Нестандартные data/charts paths вне checkout этой командой не очищаются; другие Podman-пользователи/движки и host-процессы оператор должен остановить отдельно.

## Архив и восстановление

Каждый непустой применённый `reset` создаёт приватный каталог:

```text
.cache/cleanup-backups/<UTC-дата>-<случайный-id>/
  manifest.json
  data/...
  charts/...
  ...
```

Архив сохраняет исходные байты и относительные пути. Перемещение выполняется через rename на той же файловой системе; при `EXDEV` операция останавливается, SQLite не копируется с последующим рискованным удалением. Manifest записывается атомарно с fsync и содержит полный план, список фактически перенесённых файлов и `complete`. При частичной ошибке уже перенесённые файлы остаются в указанном архиве, остальные — на прежних местах. При аварийном завершении сравните также реальные файлы архива с полным планом manifest.

Для восстановления сначала остановите **всех** писателей. Изучите manifest и возвращайте только нужные файлы по их исходным путям, не перезаписывая более новое состояние. Логовую SQLite восстанавливайте согласованно с её WAL/SHM, не только основной DB. Старые control-команды и веб-токены не восстанавливайте без необходимости. Автоматическое восстановление с перезаписью текущих файлов намеренно не предусмотрено.

Архивы могут содержать историю и чувствительные логи; каталог нового архива имеет права `0700`. Не публикуйте его. Архивы и private probes не удаляются автоматически: `reset` очищает рабочие пути, **но не освобождает место, занятое архивом**. После проверки/резервного копирования старые архивы можно удалять адресно вручную. `cache` освобождает место без архива только для восстановимых файлов.

## Уже отслеживаемые runtime-файлы

Правило `.gitignore` не снимает ранее добавленные файлы с учёта. При этой доработке runtime SQLite и lock-файлы удалены **только из индекса Git** (`git rm --cached`), без удаления рабочих файлов. Поэтому в diff есть удаления из репозитория; это ожидаемо. После коммита они продолжат создаваться локально, но не будут засорять `git status`. История Git не переписывается.

**Обновление других checkout:** коммит удаления из Git может физически удалить ранее отслеживаемые файлы в другом клоне. Перед получением такого обновления остановите писателей и сохраните согласованный backup `data/` и `config/` с учётом SQLite WAL. После обновления верните рабочие данные из backup до запуска. Не применяйте `git clean -fdx` или `git reset --hard` к рабочему проекту: игнорируемые данные и архивы не становятся ненужными.
